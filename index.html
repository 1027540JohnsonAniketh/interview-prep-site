🧠 Kernel-Level Systems Thinking

The kernel is the layer between your application and hardware. Understanding it is what separates senior engineers from staff-level systems thinkers.

What is a Kernel?

The kernel sits between your application (Elasticsearch, Redis, etc.) and the hardware (CPU, RAM, Disk, Network). It decides how resources are allocated and used.

Your App (ES / Redis / Memcache) → Kernel (Linux) → Hardware (CPU, RAM, Disk, NIC)

When someone says "learn kernels to survive in tech," they mean: understand what happens below your application so you can debug and reason about performance from first principles.

Memory: Page Cache vs Heap Memory

Heap = your app's memory (JVM-controlled). Page Cache = OS memory (Linux-controlled) that automatically caches frequently read file data in RAM.

When Elasticsearch reads data, Linux checks the page cache first. If the data is there → fast (RAM speed). If not → goes to disk (slow).

Why ES recommends ~50% heap: Leaving ~50% of RAM for the OS allows Linux page cache to store frequently accessed data, reducing disk I/O and improving query performance.
Slow Query → Page Cache Miss → Disk I/O → Higher Latency

Key insight: If you increase heap from 50% → 75%, you reduce RAM available for page cache → more cache misses → more disk reads → slower queries. The problem isn't in ES config — it's in how Linux manages memory.

CPU: Thread Scheduling & Context Switching CPU

Your code doesn't run directly on CPU — threads compete for CPU time. The Linux scheduler decides who gets a CPU core and for how long.

Context switching: CPU stops one thread, saves its state, loads another. Too many threads → excessive context switching → overhead.

Run queue: Threads waiting for CPU. If run queue > number of cores, threads are waiting even if CPU isn't at 100%.

In Elasticsearch: Too many search threads + concurrent requests → run queue grows → threads wait → slow queries. Sometimes latency is NOT about CPU usage — it's about threads waiting for CPU time.

Network: Latency, Queueing & TCP Network

Network delay is NOT just distance — it's a pipeline: App → OS network stack → NIC → routers → destination → response.

Where latency comes from: DNS lookup, TCP handshake, queueing in network buffers, packet retransmissions, serialization/deserialization.

TCP internals (critical for Redis/Mcrouter):

• Socket backlog: If too many requests arrive, they queue in the kernel network stack
• Retransmissions: Packet loss forces TCP to resend — even small % loss = big latency spike
• Congestion control: TCP slows down when network is overloaded

Redis latency spike with low CPU and fine memory? Check network: connection backlog, TCP retransmissions, packet drops. Requests are being queued in the kernel network stack, causing delays before reaching the application.

Disk: Sequential vs Random I/O Disk

Sequential read = reading a book page by page (fast, predictable). Random read = flipping to random pages (slow, disk seeks).

Even SSDs are slower for random than sequential access. Your query pattern affects disk behavior:

• Aggregations / filters → more random access
• Full scans → more sequential access
• Lucene segments in ES are optimized for sequential reads

Many small random reads are much worse for latency than one big sequential read. This is why ES uses segment merging and why storage engines (LSM trees, B-trees) are designed around I/O patterns.
🔍 5-Minute Debugging Framework

A systematic approach to diagnosing any production performance issue.

Step-by-Step Flow

Step 1: Classify — Is it doing work, or waiting? (CPU high = working, CPU low = waiting)

Step 2: Map to 4 resources — CPU, Memory, Disk, Network

Step 3: Eliminate — Check each resource, cross off what's normal

Step 4: Hypothesize — Form a kernel-level hypothesis ("page cache miss due to memory pressure")

Step 5: Validate — Use 1–2 commands to confirm

⚡ Essential Linux Commands

The only signals you need to master for production debugging.

top CPU

%us = user CPU, %sy = system (kernel work), %wa = waiting on disk

If %wa is high → CPU is waiting on disk. The app isn't slow because of compute — it's waiting for I/O.
top -b -n 1 | head -20

free -m Memory

Shows available memory and buff/cache (your page cache). Low available = memory pressure → page cache eviction → more disk I/O.

Low free ≠ bad. Linux uses "free" RAM for caching. Check available instead.
free -m

vmstat CPU Memory

r = run queue (threads waiting for CPU). b = blocked (waiting on I/O).

If r > number of cores → CPU contention (threads waiting). If b is high → disk or network wait.
vmstat 1 5

iostat -x Disk

await = I/O latency, %util = disk busy percentage.

If await is high and %util near 100% → disk is your bottleneck.
iostat -x 1 5

ss / netstat Network

Check retransmissions, connection backlog, and open connections.

High retransmits → network instability / packet loss. Full backlog → requests queued before reaching app.
ss -s && ss -ti | head -30
